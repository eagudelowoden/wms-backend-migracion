## Decisiones que debes tomar

### 1. Columnas `int` en Telefonica que el backend trata como `boolean`
En el cliente 85 son `bit`; en Telefonica son `int`: `codigosap.validacion`, `asignacionacc`, `asignacionfalla`, `multimodelo` y `accesorio.cruce`.
Con `int`, guardar o leer un CodigoSap falla (`column ... is of type integer but expression is of type boolean`).
- **Opción A (recomendada):** ejecutar `06_homologar_boolean.sql`. Telefonica queda igual que el 85 y no se toca Java.
- Opción B: dejarlas `int` y adaptar el backend por cliente (más código; no recomendable).

El script `08` te dice cualquier otra diferencia de tipo contra el 85.

### 2. Llaves foráneas
En SQL Server algunas FK estaban deshabilitadas (`NOCHECK`) y el DDL exportado **no lo muestra**. Con el 85 esto causó errores como `fk_pallet_posicion` o `fk_ingreso_cajadespacho` (filas con Id = 0 como "sin posición/caja"). Para saber cuáles lo estaban, en SQL Server:

```sql
SELECT OBJECT_NAME(parent_object_id) AS tabla, name AS fk
FROM sys.foreign_keys WHERE is_disabled = 1 ORDER BY 1;
```

Después, en `03_foreign_keys.sql` elimina esas líneas. Antes de aplicar las demás, revisa huérfanos; un ejemplo (repite el patrón por cada FK):

```sql
SELECT COUNT(*) FROM wmswdtelefonicacolombiabog.pallet p
LEFT JOIN wmswdtelefonicacolombiabog.posicion x ON x.id = p.posicionid WHERE x.id IS NULL;
```

Alternativa: no aplicar el archivo (el sistema ya funcionaba así con el 85 tras `quitar_fks_deshabilitadas.sql`). Las FK dan integridad pero cuestan algo de velocidad en escrituras.

### 3. Mayúsculas/minúsculas
SQL Server comparaba sin distinguir mayúsculas; Postgres sí. Se mantiene el criterio del 85: columnas `varchar` y `LOWER()` en las funciones (ya aplicado en `09`). No se usa `citext` salvo en las columnas de login de `general`.

## Datos

El DDL no trae datos. Para cargarlos desde SQL Server: pgloader, DBeaver (Data Transfer) o `bcp` a CSV + `COPY`.
- Las columnas `bit` ahora son `boolean`: `0/1` se convierte bien con pgloader y DBeaver; en CSV usa `true/false` o `t/f`.
- Las identity quedaron `GENERATED BY DEFAULT`, así que se pueden insertar los Id originales. Luego `07_post_carga.sql` ajusta las secuencias.
- `datetime` → `timestamp(3)` (sin zona horaria, igual que SQL Server).
- Orden de carga si ya aplicaste las FK: catálogos (`maestro`, `tipomaestro`, `codigosap`, `posicion`, `lote`, …) antes que `pallet`, `ingreso`, `empaque`, etc. Lo más simple: cargar con las FK sin aplicar.

## Equivalencias de tipos usadas

| SQL Server | PostgreSQL |
|---|---|
| `int identity` | `integer GENERATED BY DEFAULT AS IDENTITY` |
| `bit` (default `1`/`0`) | `boolean` (default `true`/`false`) |
| `datetime` / `smalldatetime` / `date` / `time` | `timestamp(3)` / `timestamp(0)` / `date` / `time` |
| `nvarchar(n)` / `nchar(n)` | `varchar(n)` / `char(n)` |
| `decimal(p,s)` | `numeric(p,s)` |
| `tinyint` | `smallint` |
| `image` | `bytea` |
| `include (...)` en índices, índice con `where` | `INCLUDE (...)`, índice parcial |

Los nombres de tablas y columnas quedan en minúscula (el backend ya los consulta sin comillas). Los índices con nombres raros (`[<Ingreso01>]`) se limpiaron.

## Cosas a tener en cuenta del backend

- **Registrar el cliente**: el cliente Telefonica debe existir en `general.cliente` con su esquema `wmswdtelefonicacolombiabog` (así lo resuelve `ClientSchema`).
- **Los 5 SP nuevos no los llama el backend Java** (se usan desde informes/BI). Solo hace falta que existan.
- **SP específicos de Telefonica con el mismo nombre que los del 85**: las funciones de `09` salen de las del 85. Si en Telefonica algún SP tiene lógica distinta a la del 85, hay que comparar ese cuerpo. El número de parámetros coincide en todos; el cuerpo no se comparó (no tengo el SQL Server original del 85).
- Las funciones que consumen `Object[]` en Java devuelven todo como `text`; ya vienen con los `CAST` del trabajo anterior.
- Hay SP que en SQL Server tenían la base fija (`WmsWdTelefonicaColombiaBOG.dbo.X`); en las funciones nuevas eso ya quedó sin prefijo y resuelve al esquema.
